## What a good rewrite fixes
Go through the trajectory step by step and check each item. Edit only where an item clearly applies.

1. Repeated work. A turn that repeats an earlier command, or checks again something the terminal already showed,
   without new information: delete it. The same applies within a turn: if one command's output is fully contained
   in another command's of the same turn (a plain `cat` next to `cat -A` of the same file), remove the redundant
   command and its output.
2. Dead ends. A turn whose output the agent never used and that the solution did not need: delete it, unless a
   later step relies on what it did or showed. The same applies to a single dead-end command inside an otherwise
   useful turn (a failed probe, an inspection whose result is never used): remove just that command and its output,
   leaving the rest of the turn intact. A turn that damages a result an earlier turn already achieved (for example
   by overwriting a required output file) is never needed: delete it together with any later turn whose only
   purpose is to repair the damage, as long as a kept turn still produces the final result.
3. Wrong statements in the reasoning. A claim that contradicts the task or what the terminal showed (a misread
   output, a wrong count, a wrong belief about what a command does or about which part of the output is the
   command's own message), or that states as an observed fact something the terminal had not yet shown: correct
   that statement, nothing more. This also applies to the action's analysis and plan (correct the wrong sentence,
   keep the commands byte-identical) and to a command sketched in the reasoning as an alternative: fix or remove a
   sketch that would not do what the text claims. A correct alternative, a defensible interpretation, or an
   approximation whose conclusion is right is not an error; if you are not sure the statement is false, leave it.
   If you rewrite a sentence, re-check every claim in the new text against the command and the terminal; never
   carry over clauses that do not match what the command actually does.
4. Garbled or corrupted text. Corrupted tokens, stray characters, HTML entities, truncated words, misspelled
   command or file names, broken operators (`gname` for `grep`, `&gt;` for `>`), or broken fragments: replace only
   the damaged span with the minimal text the agent intended, or delete a fragment that only duplicates other
   text. Check both reasoning and action analysis/plan; fix the latter with set_command keeping commands
   byte-identical, which does not count toward the action-edit limit. Do not rewrite surrounding text.
5. Circling reasoning. Long back-and-forth that ends at the right decision: cut the repetition and the abandoned
   alternatives, and keep the agent's own sentences for the considerations that matter and for the decision.
   Abandoned alternatives include candidates proposed and retracted inside a single reasoning block: superseded
   command proposals, code blocks of commands never run, enumerated options the agent did not choose, stated
   intentions it never acts on. Cut these even when they are not wrong, and above all when they are. If the passage
   also contains wrong statements, trim the circling first rather than patching individual sentences inside it.
   Do not summarize the reasoning in your own words.
6. Detours in actions. An action that takes an indirect or trial-and-error path when the direct one was already
   evident — from what had been observed, or from what the agent's own reasoning at that step had already worked
   out: replace it with the direct action. If the agent could not have known yet, leave it.
7. Fragile commands. A command that worked by luck, or does something other than what the reasoning says or the
   task explicitly requires: fix it, as long as the result the task checks stays the same. Typical cases: a
   redirection order that loses stderr or covers only the last command of a pipeline or group; an unquoted
   pattern; an option that does not provide the behavior the task names; an `echo $?` that reports a later
   command's status instead of the intended one. Make the smallest fix that removes the flaw, where the command
   first runs — keep the agent's own commands and utilities, preferably a formulation the agent itself wrote. Do
   not replace a command that is correct for the observed inputs with a stricter or more robust equivalent, and do
   not add hardening or reporting the agent never considered. If a later step must report an earlier command's
   exit status that was never saved, capture it at the step that ran the command and update that step's terminal
   output; never edit a later step to claim a status it did not measure.
8. Reasoning that misdescribes its own action. When the reasoning, analysis or plan says the step will only
   inspect or check but the keystrokes also change state (create or modify files), or announces actions the
   commands never perform: add the missing mention to the reasoning in the agent's own words. Do not change a
   working command to match the reasoning.

## What a good rewrite leaves alone
9. Correct reasoning and correct actions, even if you would phrase or do them differently. No changes of style,
   formatting or command preference.
10. The commands that produce the task's final result. Change one only if its observable output or effect differs
    from what the task asks for, or it violates an explicit requirement (a named tool, files to preserve). A
    different implementation with the same observable result is correct, even if the task narrates a method.
    Do not tighten a pattern or filter that already selects exactly the right inputs on the observed tree, or
    switch between execution forms with identical observable results to enforce a stricter reading of ambiguous
    wording about exactness or batching. If only the plan misdescribes a working command, fix the words, not the
    command. If you change a command, the terminal output you write must be exactly what it would print.
11. The structure: do not add, merge or reorder turns.
12. Steps {protected}: they complete the task. Do not delete them or change their commands or terminal outputs; you
    may correct wrong statements in their reasoning, and in the analysis and plan of their action (set_command with
    the same commands). If such a step's command shows something other than what the trajectory relies on (for
    example, it echoes the exit status of a verification command rather than of the solution command), record the
    truthful observation at an earlier editable step and adjust the step's reasoning so it does not present that
    output as the claimed fact.

## Keep it consistent
13. No hindsight. What a step reasons or does may only use the task and what the terminal had shown before that
    step, as edited.
14. After any edit, sweep every step, earlier and later, including protected turns. Read the reasoning and each
    action's analysis and plan claim by claim, including quoted commands. Fix every occurrence of a corrected
    claim, stale command quote, unsupported recap, or description of removed commands or of behavior a kept
    command does not have. This includes counts, values, timestamps and exit-status claims. Update protected
    action text with set_command, keeping commands byte-identical. Fix terminal outputs affected by changed
    commands or state (files, permissions, timestamps), subject to item 12. If only a deleted command supplied a
    claim's evidence, retain an evidence-producing command or remove the claim.
15. Clean cuts. When you delete reasoning text, delete whole lines or blocks in a single "old" quote, together
    with their line breaks and the blank lines that separate them; never replace deleted text with a lone space.
    After editing a step, reread its full reasoning: it must read as continuous prose, with no runs of blank lines,
    whitespace-only lines, stray spaces, orphaned list markers or half-sentences, and no dangling connectives
    ("However", "But more importantly") where text was removed. Extend or trim the deletion until the remaining
    text reads as something the agent could have written.
16. A terminal output you write must be what the real shell would print, in the same format as the surrounding
    outputs, including the first line ("New Terminal Output:") and the shell prompt lines. Never write a success
    the commands would not produce.

## Decide
17. Small: delete or replace the action of at most {budget} of the {n} steps. Reasoning edits — including
    correcting the analysis and plan text of an action whose commands stay byte-identical — do not count toward
    this limit; check the reasoning of every step for the items above, including steps whose commands you keep.
    If the trajectory is already clean, answer with no edits; when in doubt, leave a step as it is.
18. Decide whether the edited trajectory would still pass the task's tests. If it would not, answer with no edits.

## How to write the edits
- edit_thinking: "old" is an exact quote from that step's reasoning, copied character for character (a sentence, or
  the whole lines or block you delete), that occurs exactly once there; "new" replaces it, and an empty "new" deletes it.
- set_command: the complete action JSON the agent writes: {"analysis": "...", "plan": "...", "commands":
  [{"keystrokes": "...\n", "duration": 0.1}], "task_complete": false}.
- set_terminal: the full terminal output after that step.
